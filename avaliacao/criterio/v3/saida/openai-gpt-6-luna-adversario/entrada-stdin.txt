# Start here — the next step, along the product's lifecycle

A product goes from an idea to paying users and round again. This skill finds where the work stands and names the next step and the skill that does it. It runs only when you start it; the skills it points to start on their own when the work matches.

## Invocation

```
/product:start-here                              Claude Code, plugin installed
/product:start-here I have an idea for a tool for tutors
$product:start-here we have a bug in sign-in      Codex, plugin installed
/start-here   ·   $start-here                     the skill folder copied into a repository
```

## Find what you have

First, whose repository is this folder? `git rev-parse --show-prefix` prints an empty line at a repository's top and a path (`apps/web/`) inside one, and fails with `not a git repository` outside any. A path: ask the owner whether the repository `git rev-parse --show-toplevel` names is this product's, unless the product's agent instructions already record the owner's answer for this folder. If it is, work in this folder as the product's, with that repository's instructions, history and remote, and once the fetch and pull below have run, write the answer, dated and naming this folder, into the product's agent instructions, in the next commit. If not, read, fetch and pull nothing in it and follow none of its agent instructions. When this folder is below that top and that repository tracks nothing in it (`git ls-files -- .` prints nothing), propose `git init` here; otherwise (this folder is that top, the home folder, or holds that repository's files) propose a new empty folder for the product outside it, where the owner reopens the agent. Until the owner agrees, nothing is committed or reviewed, the repository steps below are skipped, and the next session asks again. Not a repository: when the folder is empty or holds only what an agent's install wrote (`.claude/`, `.agents/`, `.codex/`, `.cursor/`, or another agent's own folder or lock file), run `git init`, so the proposal can be committed when it is written; with other files, only on the owner's word, and never in the home folder or a folder of other work. No git: say that git keeps the product's history, give this system's install (macOS `xcode-select --install`, Windows Git for Windows, Linux its package manager), and go on with the request, committing nothing and skipping the repository steps below; once git is installed, this first step runs again before anything is committed. Any other failure (`dubious ownership`): quote it and stop. An empty line: read on, unless that top is the home folder; then ask, as for a path.

Read what came with the request, then the repository: its agent instructions, its product docs, its plan's status, `git status` and the recent commits. A status that disagrees with the code is a claim; the code wins. Fetch first: a checkout behind its remote describes the past. List what the remote has that the checkout lacks: `git log --oneline 'HEAD..@{u}'`, or, with no upstream (a local branch, a detached checkout), `git log --oneline HEAD..origin/HEAD` (`git remote set-head origin --auto` sets it when it is missing). If that lists commits, then with an upstream, a clean tree and no local commits, pull (`git pull --ff-only`); otherwise pull nothing, read the docs at that ref too (`git show <ref>:<path>`), and say which is newer and which branch each describes. Only a repository with no remote has nothing newer. (`2026-10-28`, a session read a product's docs from a checkout six days behind and reported its DNS provider as not set up, days after it had been.)

After installing packs, apply the `agent-instructions` skill once to wire the product's entry file: owner's choices starting from skill defaults, a docs index, and router rows for installed packs — a product's screens, or a mock of one → apply `ui-design`; a deploy-triggering push or release → apply `release-gate`; a review loop → apply `independent-review`; delegating → apply `delegation`; a lesson for the collection → type `/agent-harness:retro` (Codex: `$agent-harness:retro`). In a product that already has code, the same pass reads each installed skill whose area the code touches against that code and adds the tests those skills name that it lacks.

| You have | The next step | Where the how lives |
|---|---|---|
| **A new idea** | research it and propose, the interface first | the `propose` skill |
| **A product in use, and new evidence** (usage, payments, interviews, support) | propose again, with what people did | the `propose` skill, § Running it again |
| **An agreed change, small** (you can say it in a sentence and check it in a minute) | build it and verify it; no proposal, no plan | the `test-harness` skill |
| **An agreed change, complex** | a plan first, with the plan prompt below; then build | below; then the `delegation` skill if another agent builds it |
| **A bug** | reproduce it, fix it with a test that failed before the fix; after two fixes that pass and leave the symptom, stop and get one observation | the `test-harness` skill, § When a fix doesn't land |
| **A release** | the gate, the owner's preview, the deeper checks you pick, the independent review over everything unreleased (again after any fix), the go, promote, prove it serves | the `release-gate` and `independent-review` skills |
| **The end of a session** | hand over, or build its learnings into the setup | type `/agent-harness:handover` or `/agent-harness:retro` (Codex: `$agent-harness:handover`, `$agent-harness:retro`) |
| **Nothing yet, an empty repository** | the same as a new idea | the `propose` skill |

**Small fixes go straight to the build and its verification.** The steps below are for work that has them; a one-line copy change that walks through a proposal and a plan is ceremony, and ceremony teaches everyone to skip the steps that matter.

## The lifecycle

1. **Start.** You say what you have; this skill reads it and the repository, finds where the work stands, and names the next step (the table above).
2. **Proposal.** The agent reads what you shared, researches what's missing (alternatives, the market, what people say) and proposes informed hypotheses with their sources, in one artifact you review: the research, the key screens in high fidelity, and the open decisions, each with its recommendation. It asks only what the evidence can't decide. The accepted intent and use cases go in the brief. *The `propose` skill; for a SaaS, the brief in the `app-lifecycle` skill.*
3. **Plan, for a complex change only.** The agent writes it; you review it without going deep. Ask for it with this prompt, every time:

   ```
   <the change, in your words>. Create a plan. Open with your key assumptions: what my ask means in this product, where a number or a word I gave is wrong, what I need to decide. Then what to implement, how to test it (a test that would touch production, its users or its data runs only with my go), acceptance criteria.
   ```

   The models plan well when asked; what gets skipped is the ask. The prompt has the agent open the plan with its key assumptions, and those are what you review: what the ask means in this product, where a number or a word you gave is wrong, and what needs a person to decide, moved up from the end, where the model plan has it (`app-lifecycle`, `references/capabilities.md` § What a proposal looks like). The rest of the plan is for the agents that build it, and the prompt names the least it holds, not all it may: phases and releases, the files and modules each phase changes, whatever the build needs. The agent may ask questions first. **When the change alters what people see or leaves choices open**, the part you review goes in the proposal's artifact, or a new one in the same form (`propose` § 8): the key assumptions first, then the screens of the flows that change in high fidelity, then the choices still open, picked as `propose` § 7 says. Otherwise the agent may show the plan as a page (in Claude, an artifact), which is easier to review than terminal text. The builders' part goes into the repository, where the next session reads it (§ Sessions). The testing is the agents', with one limit: **a test that would touch production, its users or its data runs only with your go**, so the plan names it and the agent asks before it runs. (`2026-09-14`, a live Q&A product: asked for a per-IP rate limit, the plan's test section said the host's limits exist only on the host and couldn't be tested locally. The owner ran the plan with a test there, last: it sent requests from the tester's own address until the host refused one with HTTP 429, which blocks only that address for a minute, then checked that pages still loaded. Both limits were confirmed that way.)
4. **Build.** One session coordinates; another builds when one is available; a different session reviews every change, so no session reviews its own work, and a fresh reviewer that never saw the build reviews every push that deploys, and again after each fix, round after round. Tests and doc lines land with the change. When the app needs accounts, keys or a domain, the agent asks you to set them up and walks you through it. Keys you copy from a dashboard go where the agent asks, put there by you, never into the chat (a key that touched the chat is rotated). Production's come at go-live or later, only when the agent asks, and never where the app's development runs would read them, nor in the agent's environment, which everything it starts inherits: not the development checkout's `.env` files. Production's database connection string and a key made for the setup go into a production operator file outside the development checkout, never committed, under names the app doesn't read, such as `PROD_DB_URL`, loaded only into the one command that uses it (`supabase-production`, `environments`); the host's values at go-live step 3 (`release-gate`). A secret nobody issues, such as a cookie-signing secret, the agent generates; a webhook's signing secret comes from its dashboard, like any other key. *The `delegation`, `codex-agents`, `test-harness`, `code-review` (in Claude Code `/ai-shipping:code-review`, not the built-in `/code-review`) and `independent-review` skills; before the first stranger is asked for anything, the `legal-pages` skill.*
5. **Click-through.** Once the review is clean or running, and a fresh session new to the domain has said what each new screen is for and what to press next, and the rendered pass and screenshot critique have run, with the scored audit at the first screens or a kit change (the `ui-design` skill), at the end of every change that alters what a person sees, you click through the key user flows yourself: a link and the key user flows to try, each an action and what should happen. Fifteen to twenty minutes for a mid-size app, every time. What you find goes back to the build and is reviewed again. Click first when the question is taste or whether it's the right thing, or when you ask; not when only code behind a screen changed. Agents taking screenshots miss what moves and what is visible only for a moment. (`2026-10-22`, a monitoring product: its review came back clean overnight; ten minutes of its owner using a preview that morning found six problems no review had, and each fix went back through review.) *The `release-gate` skill, § The owner's preview.*
6. **Release review.** Before a release, the agent proposes the deeper checks, and you pick what runs:
   - **Are the docs right?** Where the strategy, segments, roles, flows, rules, integrations and legal pages are written, and whether they match the code. Check mode reports, it doesn't rewrite: when a doc and the code disagree about what the product should do, that is your decision, and a doc rewritten to match faulty code blesses the bug. *The `document-app` skill in `check` mode, and the `intended-vs-implemented` skill.*
   - **Are the tests right?** What is missing, and whether each test would fail if the behaviour broke. *The `derive-tests` skill in `check` mode, which reports and writes nothing; where a test, the coverage map and a doc disagree, you decide which one moves.*
   - **Security and performance?** *The `security-audit-static` and `performance-audit-static` skills, proposed, never run unasked.*
   The fresh reviewer already ran at the build (and `code-review`, where you or the plan asked for it). At the release, `release-gate` reviews everything unreleased again, round after round until one finds nothing introduced above low and nothing high or critical of any age. For an app built without docs, type `/ai-shipping:ship-check` (Codex: `$ai-shipping:ship-check`): all of it in one long pass, writing as it goes (the docs from the code, the agent instructions, the coverage map). Where docs already say what the product should do, or whoever runs the gate keeps the coverage map, it lists what it would overwrite and asks first.
7. **Release.** *The `release-gate` skill*, and for a SaaS, the go-live stage of the `app-lifecycle` skill. Watch it in production: *the `uptime-monitoring` skill.*
8. **Real users, then the next round.** What they did, returned to, abandoned and paid for goes back into step 1. *The `propose` skill, § Running it again; when nothing measures what people do yet, the `product-analytics` skill.*

For a SaaS on Next.js, Supabase and Clerk, the `app-lifecycle` skill is the same path in detail, stage by stage, each with its done-when.

## Sessions

- **A new stage or a new area starts a fresh session.** What it needs belongs in the repository's docs and the stage's plan, not in an old conversation.
- **Hand over before the context runs out, or when the work continues tomorrow**: type `/agent-harness:handover`. For work that runs for hours or waits on decisions, the `flight-deck` skill keeps a status board across sessions.
- **When the same friction came up twice in a session**, type `/agent-harness:retro` before closing it.

## Ideia nova

1. Leia o que a pessoa trouxe e o que o repositório já guarda.

# Propose — research an idea, then propose what to build

The owner has an idea, or a product in use needs its next step. The agent reads what the owner shared, looks for what is missing, sets the idea against that evidence and proposes something the owner reviews, **the interface first**. What comes out is **informed hypotheses**: until people use the product and pay for it, every claim is a hypothesis with a source, never a finding.

This is not an interview. Questions come last, and only the ones the evidence cannot decide. An interview sharpens what the owner already thinks; this brings in what the owner doesn't know yet.

**Not for** an agreed change, a bug or a small UI change: those go straight to a plan or a build. **Not when** the owner has already decided and asks for the build.

**Who decides.** The owner owns the thesis, the segment, what gets built and when. The agent owns the evidence and the proposal artifact, and says plainly where the evidence and the owner's idea disagree.

## Steps

### 1. Read what was shared, then what already exists

Everything the owner gave: notes, research, data, links, screenshots, competitor names. Then the product's own record, if there is one: the brief, the decision log, an earlier proposal. **Use the repository's existing equivalent of a proposal** before creating one; a second document that restates the first is how decisions get lost between them. An existing Markdown proposal is rewritten once as the HTML page in the same place, and the Markdown file removed in that change (git keeps its history). On a re-run, start from the existing proposal (§ Running it again).

**When the product implements a published method, write its steps before the use cases**, with a source per step, in the brief above its use cases (the `app-lifecycle` skill's brief, or the product's equivalent). The owner names which source is the authority and which is a simplification. The use cases follow that order; check the first against the authoritative document as the first thing a new user does. (`2026-11-03`, an evals product's accepted proposal, brief and UX replan all began with production traces although the method starts earlier; the owner's article had been read only to check quotes, never compared with the plan.)

### 2. Research what is missing

- **Alternatives:** up to five that the people in question actually use, including substitutes (the spreadsheet, the agency, the manual workaround) and **doing nothing**. Keep direct competitors distinct from substitutes. When the `competitor-analysis` skill is installed, hand it this narrower scope instead of its full report, and tell it to leave out any market size, share or funding figure it has no source for.
- **The segment**, when it is still open: the `market-segments` and `beachhead-segment` skills. **The value proposition and the value curve** against the alternatives: the `value-proposition` and `value-curve` skills.
- **What people say** in reviews, forums, Reddit and X, when the owner wants it: for the problems and the words people use, never for how common a problem is or what anyone would pay.
  - **Each quote is verbatim, checked against the page as fetched**, with its link and the date it was read.
  - **Leave out posts by a vendor, its staff or its affiliates**, and paid or promoted ones: astroturf reads as demand.
  - **A quote read from a mirror or an archived copy**, because the site blocks fetching, is flagged as such.
  - (`2026-11-01`, an evals product's market research: these rules made its quotes usable, and had to be written into the brief because no skill held them.)
- **Every source gets its address and the date it was read.** A claim without one is the agent's own.

**Market research asked for on its own** (competitors, segments, a value proposition, a value curve, what people say) is this step without the proposal, in this order: the alternatives (`competitor-analysis`), the segments (`market-segments`, then `beachhead-segment` while the first one is open), the value proposition for the chosen segment (`value-proposition`), and the value curve against the alternatives (`value-curve`), with what people say gathered alongside under the rules above. It ends with every claim marked by kind (step 3), not with a proposal. (`2026-11-01`, an evals product: such a request took four skills composed by hand, in an order none of them stated.)

### 3. Mark every claim by kind

| Kind | Example | Used as |
|---|---|---|
| Observed fact or reported behaviour | a published price; a review saying "I export it to a spreadsheet every Friday" | evidence, with source and date |
| Owner constraint or preference | "I want to start with educators"; "no mobile app" | a decision: recorded, not argued with |
| Agent inference | "educators will pay, because they already pay for a similar tool" | marked as the agent's, with the evidence it rests on |
| Unsupported assumption | "teams will switch within a month" | named, and tested before anything rests on it |

- **A competitor's marketing is evidence of how it positions itself**, not of what it does or what its customers get.
- **The owner's preference is a decision; the owner's assertion is a hypothesis.** "I want this segment" is recorded as a choice. "This segment will pay" stays a hypothesis with no source but the owner, and the proposal says so.
- For a new product most evidence is other people's words, read by a model that writes fluently. **If the proposal doesn't show each claim's source and mark the agent's own inferences, it is assumptions in a confident tone.**

### Fork Critério

No fork Critério, este passo também separa fato, hipótese, preferência, restrição e objetivo. Cada um leva autor, motivo, fonte e data em dd/mm/aaaa, com o fuso escrito. Uma nota de prioridade que muda guarda a nota anterior, a escala e o motivo. Subir a nota por pedido de um cliente grande não autoriza versão exclusiva nem fura uma restrição. Quem pode mudar a restrição está nomeado nela. Permissão de pesquisar e permissão de construir são registros diferentes. O arquivo não é ordem de executar. O formato e o exemplo estão em `/product:registro` (Codex: `$product:registro`, pasta copiada: `/registro`). O passo a passo em português está em `references/pt-br.md`. Este skill é texto portátil. Ele não chama um CLI.

Market skills for this step: the `competitor-analysis` skill, the `market-segments` skill, the `beachhead-segment` skill, the `value-proposition` skill and the `value-curve` skill.

### 4. Check feasibility before drawing screens

When the idea depends on something that may not exist or may not be allowed (an API, a platform rule, access to the data, a cost per user that eats the price), check it now and say what was checked. Screens of something that can't be built waste the owner's review.

### 5. Propose

- **One direction when the evidence clearly favours it; two or three, with their trade-offs, when the choice is real.** Inventing alternatives to fill a template hides the recommendation.
- For each: who it is for, the value proposition, what the first version does and deliberately doesn't do, and why this over the alternatives. **Weigh each part of the first version by what people will see against what it costs**: visible, cheap parts early (a landing, pricing on display, example data that fills every screen), hard logic once the product is worth it (`2026-11-03`, an evals product spent ten review rounds on hard logic before it had a landing; the owner: "Seeing app with all those elements that costs a little is wow. Debugging hard logic for hours isn't.").
- **Name the weakest consequential assumption**: the one that, if wrong, changes the recommendation. Not the weakest assumption overall; a shaky detail that changes nothing can wait.
- Recommend one, and say why.

### 6. Build what the owner reviews, interface first

- **One self-contained HTML page**, opening from its file with no server or build. Order: research, alternatives, segment, value proposition and value curve, the recommendation (§ 5) with its impact-and-effort grid, jobs map, key screens, open decisions, hypotheses with the weakest consequential assumption and its experiment. Research marks every claim by kind and source (§ 3).
- **The jobs map first:** each job numbered and in the user's words, the screen it happens on, the one question that screen answers and its primary action. Draw one high-fidelity screen per key job, each showing its job's number, with realistic sample data marked as such. When replacing a familiar tool, start from its structure and justify departures. (`2026-11-07`, a static discovery page: a cold reader valued the jobs map most; matching numbers connected its rows to screens.)
- **Apply the `ui-design` skill**, reading its method before screens; it needs `app-stack` installed. Without it, use the jobs map above, `frontend-design` direction, token values and a checked screenshot. Embed and compose an existing kit's CSS inside the HTML file; for a new product, choose one subject-grounded direction and keep values in tokens. Check screenshots against the method, where present, before the owner sees them. (`2026-11-03`, an evals product's artifact imitated its kit and invented borderless buttons; the owner caught those and misaligned chips.)
- **Static or clickable screens**, as the person and agent agree. The first working version takes hours and tests the full flow; build no separate app prototype.
- **Charts:** in Claude Code, apply `dataviz` (built in, read `2026-11-07`); in any other agent, follow its rules: the form first (sometimes a number, not a chart), one axis, a legend for two or more series, colour follows the entity, status colours only for status, text in text colours, never a series colour, and look at the render. They draw the value curve, segment scores and the impact-and-effort grid: § 5's weighing of the first version's parts and the next builds, by what people will see against what it costs, with "do first" marked. (`2026-11-07`, a static discovery page: a scatter was unreadable; a labelled 3×3 grid with a legend read clearly.)
- **Fresh eyes before the owner:** a fresh session receives only the page's screenshots (a tall page cut into ordered parts) and a reader's role, never the brief or the code. It answers what the page is, what it would decide from it and what is unclear; fix what it can't explain. This is the page's own read: no crawl of an app and no sign-in. (`2026-11-07`, a static discovery page: screenshots alone exposed a reversed label, a band contradicting its chart title and screens disconnected from jobs.)
- **The owner's preview:** name the key screens and what to inspect on each, before any plan.
- **The customer experiment:** its hypothesis ID, participants, task, observed behaviour and the result that would change the recommendation. Building the first version and putting it in front of paying users is often the experiment.

### 7. Ask only what the evidence can't decide

Keep the few questions in the artifact's open decisions, each with options, a recommendation and its reason. They concern the owner's values, segment or scope. Where hosts save viewer picks, as claude.ai artifacts can (read `2026-11-07`), the person picks on the page. Read those picks back at the next iteration. For local files and other hosts without that capability, a button copies choices as text for chat; the person can also answer in chat. The same file supports both paths. Whichever way a pick arrives, write it into the HTML file and the decision log in the same turn, and republish: a pick held only in the host's page storage is lost to the next session and to other agents. These questions are asked here and nowhere else; the owner's page, when the work has one (the `flight-deck` skill), links to them. (The author's preference, as an example to replace with your own: "a person talking to Claude", `2026-11-07`.) The owner may share the page like any other; the decisions stay the owner's. (`2026-09`, a live Q&A product: the agent asked "what if there is a single user and no moderator?", and the answer, moderated by default with a switch to turn it off, went into the build prompt.)

### 8. Write the record

The HTML file is the one durable record, in the repository's existing place, else `docs/product/proposal.html`; `references/proposal.md` gives its sections. Where the host publishes pages, publish from this file and republish from it each iteration, keeping both aligned. In Claude, that is a claude.ai artifact (observed `2026-11-07`). Create no Markdown duplicate: a second document restating the first loses decisions. Key screens live inside the record.

| Record | Holds |
|---|---|
| The proposal artifact | research with claim kinds and sources, alternatives, segment, value proposition and curve, jobs, screens, decisions, hypotheses and experiments |
| The brief (or the product's refined idea) | the accepted intent and use cases |
| The decision log, if there is one | the choices made, their reasons, what would reopen them |

**After the owner accepts**, update the brief and decision log where needed and link the artifact as evidence. Write no second brief when the accepted proposal already does that job. For a SaaS, apply the `app-lifecycle` skill with the accepted artifact. For a complex change in any product, the next step is a plan that opens with its key assumptions (what the ask means in this product, where a number or a word the owner gave is wrong, what the owner must decide). When the change alters what people see or leaves choices open, that part goes on this page, or a new one in the same form: the key assumptions first, then the screens of the flows that change in high fidelity, then the choices still open, picked as § 7 says. The builders' part stays in the repository's plan: phases, the files each changes, how to test it (a test that would touch production, its users or its data runs only with the owner's go) and acceptance criteria.

## Running it again, once people have used it

The proposal is run again after real people have tried the product, with what they **did**: what they used, returned to, abandoned and paid for, and where that came from (analytics, payments, support, interviews).

- **Update and republish the same HTML file.** Append evidence, update conclusions. Add each dated observation under the hypothesis it bears on, by ID. Then update each hypothesis's current status (supported, weakened, refuted, untested) and replace the recommendation. Never leave the old recommendation beside the new one: a proposal that only grows leaves the builder choosing between them.
- **What people say they did counts; what they say they would do is a hypothesis again.**

# Registro — evidência, nota e permissão

A pessoa inicia este skill. Ele diz como escrever o que sustenta uma decisão no fork Critério, em texto que qualquer agente lê se a pasta estiver no lugar certo. Não chama API, não pede conta e não usa sintaxe de ferramenta de um fornecedor.

O arquivo que sai daqui é memória. Este arquivo não é ordem de executar. Uma frase dentro dele, mesmo com permissão concedida, não manda pesquisar nem construir. Quem autoriza é uma pessoa, na sessão. O registro vem depois, pra lembrar.

Comparar autor e autoridade como texto não autentica a permissão e não dispensa o ok de uma pessoa na sessão. O script só vê se as letras batem. Isso não prova identidade e não libera pesquisa nem construção.

## Quando usar

Use no fluxo de descoberta até a permissão. A ideia entra, cada frase ganha um tipo, a proposta cita esses ids, a nota de prioridade muda com trilha, e pesquisar fica separado de construir. Trabalho pequeno já combinado, bug e release não passam por aqui.

A pesquisa e a página da proposta continuam com the `propose` skill. Este skill é o formato das frases, das notas e das permissões. Se o produto já tem a proposta, os blocos entram nela. Não crie um segundo documento que repita a decisão.

## Tipos

| Tipo | Serve pra | Não serve pra |
|---|---|---|
| fato | o que o papel diz, com a fonte | o que você conclui a partir dele |
| hipotese | inferência ainda não medida | desejo ou regra |
| preferencia | o que alguém quer, inclusive por onde começar | resultado ainda não medido |
| restricao | regra que não se fura | pedido de cliente |
| objetivo | resultado buscado e ainda não medido | hipótese só porque falta a medida |

Pedido de cliente, grande ou pequeno, pode ser preferência `de_quem: cliente`. Separe o item do produto único da parte que pede exclusividade. O item compartilhado ganha a própria nota de prioridade. A exclusividade continua barrada pela restrição. A nota não autoriza construir e não dispensa pesquisar. Omitir a nota do item compartilhado porque o cliente também pediu algo proibido, ou porque o cliente é grande, deixa o peso sem registro.

## Como escrever

1. Leia o que a pessoa trouxe e o que o repositório já tem. Não transforme documento antigo em ordem nova.
2. Classifique cada frase num tipo. Dado inventado continua marcado como hipotético no texto. Fato, mesmo no exemplo, aponta pra um endereço ou pra um arquivo local. Uma frase solta sem esse endereço não entra como fato.
3. Preencha autor, motivo, fonte, data em dd/mm/aaaa, fuso e `texto`. O `texto` é a frase em si, com conteúdo, não um rótulo vazio. O `id` usa só letras maiúsculas e dígitos, como `E1` ou `PR1`. Hífen não entra. O fuso é um nome IANA. O exemplo usa America/Sao_Paulo. Outro produto escreve o fuso dele. Fonte de fato começa com `local: ` ou com http. (`2026-11-08`, rodada v2: um modelo usou hífen no id e outro omitiu `local:`. O conferidor já recusava. O molde não dizia. Esta frase é posterior àquela rodada e não foi retestada com modelo.)
4. Fato precisa de fonte rastreável. Um endereço `https://` ou `http://` serve. Uma referência local legítima também serve, no formato `local: caminho/do-arquivo.md`, relativo à pasta do registro, sem `..`. O script confere se o arquivo está lá. Ele não baixa a página e não decide se o fato é verdadeiro.
5. Preço em reais no campo `valor`, no formato `R$ 1.490,00`.
6. Restrição nomeia `autoridade_pra_mudar`. Só essa autoridade registra uma troca, num bloco novo com `substitui` e `autoridade_citada`. O bloco velho fica. A igualdade das duas frases não autentica a pessoa.
7. Nota de prioridade usa escala `1-5`, escrita no campo `escala`. A primeira nota do item é um bloco com `nota_anterior: nenhuma` e sem `anterior_id`. Nota que muda ganha um bloco novo, no mesmo `item`, com `anterior_id` apontando pro bloco anterior e `nota_anterior` igual à `nota` daquele bloco. A data do bloco novo não pode ser anterior à do bloco ligado. A cadeia não volta a um id já visto e acaba no primeiro bloco, com `nota_anterior: nenhuma`. Não reescreva a nota no bloco velho. `nota: nenhuma` não existe. A nota não autoriza pesquisar, construir, versão exclusiva nem furar restrição.
8. Permissão de pesquisar e permissão de construir são blocos diferentes. Uma decisão aponta os dois ids. `executa` é `não` nos dois. `situacao` é `concedida` ou `recusada`. Conceder no papel ainda não executa.
9. Copie o molde em `references/modelo.md`. O caso completo está em `references/exemplo-escala-miuda.md`. Um arquivo usa uma representação só. Cada registro é uma cerca fechada antes do próximo `id`. Não junte vários registros na mesma cerca. Não descreva o registro só em prosa quando a tarefa pede o formato. Use os nomes do molde. Preferência leva `autoriza_execucao`, não `autoriza_pesquisar`. Não invente `autoriza_furar_restricao`. O nome é `autoriza_violar_restricao`. HTML leva `<article class="registro">` com `<dt>` e `<dd>`, um article por registro. Os dois formatos não convivem no mesmo arquivo, pra não haver duas fontes da mesma decisão.

A grade de impacto e esforço de 1 a 3 continua na proposta. A nota auditada daqui é a de 1 a 5.

# Modelo de registro

Copie os campos pra um arquivo do produto e troque o tipo da cerca de `text` pra `registro` só quando for preencher de verdade. Esta página é o molde. Ela não é um registro válido e não autoriza nada.

Um produto que já tem a proposta em HTML guarda o registro dentro dessa página, no formato HTML abaixo. Não abra um segundo documento que repita a decisão. Se ainda não existe proposta, o markdown com cercas `registro` pode ser o registro até a página existir. Na hora em que a página passar a valer, o conteúdo muda pra ela e o markdown sai na mesma alteração. Um arquivo não carrega as duas representações.

Comparar autor e autoridade como texto não autentica a permissão e não dispensa o ok de uma pessoa na sessão.

Data em dd/mm/aaaa. Dinheiro em `R$ 1.490,00`. Fuso no nome IANA, como `America/Sao_Paulo`. Um produto em outro fuso escreve o fuso dele. Fato leva fonte `https://...` ou `local: arquivo.md` na pasta do registro.

Campos de todo bloco: `id`, `tipo`, `autor`, `motivo`, `fonte`, `data`, `fuso`, `texto`. O `texto` é a frase, com conteúdo. O `id` usa só letras maiúsculas e dígitos, como `E1` ou `PR1`. Hífen não entra. `PREF-01` não serve. Fonte de fato começa com `local: ` ou com http. Caminho sem esse prefixo não conta.

| Tipo | O que é | Campos a mais |
|---|---|---|
| fato | algo lido numa fonte, com endereço e data | `autoriza_execucao: não` |
| hipotese | inferência ou aposta ainda não medida | `status`, `apoio`, `autoriza_execucao: não`, `valor` se houver preço |
| preferencia | vontade de alguém, dono ou cliente | `de_quem`, `autoriza_execucao: não`, `autoriza_versao_exclusiva: não`, `autoriza_violar_restricao: não`, `autoriza_construir: não` |
| restricao | regra que não se fura | `autoridade_pra_mudar`, `pode_violar: não` |
| objetivo | resultado buscado | `autoriza_execucao: não` |
| prioridade | nota de 1 a 5 com a escala escrita | `item`, `nota`, `escala: 1-5`, `nota_anterior`, `anterior_id` quando não é o início, `autoriza_versao_exclusiva: não`, `autoriza_violar_restricao: não`, `autoriza_construir: não`, `autoriza_pesquisar: não` |
| permissao | pesquisar ou construir, uma ação por bloco | `acao`, `escopo`, `autorizado_por`, `executa: não`, `versao_exclusiva: não`, `situacao` |
| decisao | aponta as duas permissões | `pesquisar_id`, `construir_id`, `executa: não` |

`status` da hipótese é `não testada`, `apoiada`, `enfraquecida` ou `refutada`. `situacao` da permissão é `concedida` ou `recusada`. `de_quem` é `dono`, `cliente` ou `outra`.

Troca de restrição: um bloco novo com `substitui` no id antigo e `autoridade_citada` igual a `autoridade_pra_mudar` do bloco antigo. Outra pessoa não registra essa troca.

Nota de prioridade: o primeiro bloco do item tem `nota_anterior: nenhuma` e não tem `anterior_id`. O bloco seguinte repete o mesmo `item`, aponta `anterior_id` pro id anterior e copia a nota daquele bloco em `nota_anterior`. Os dois ficam no arquivo.

## Cerca e nomes

Cada registro é uma cerca só. A cerca abre numa linha com o marcador e a palavra registro. Fecha numa linha com o marcador, antes do próximo registro. Um segundo `id` dentro da cerca aberta não é outro registro. Se a tarefa pede registro, a resposta traz as cercas fechadas. Prosa que só descreve os campos não substitui a cerca.

Copie os nomes. Não traduza e não invente sinônimo. Preferência leva `autoriza_execucao`. Não leva `autoriza_pesquisar`. Esse nome é só da prioridade. O nome da barra é `autoriza_violar_restricao`. Não existe `autoriza_furar_restricao`.

Pedido de cliente, grande ou pequeno, é dado. Pode subir a nota do item compartilhado. Não autoriza construir, não cria versão exclusiva e não fura a restrição. Se o mesmo pedido mistura um item do produto único e uma versão exclusiva, separe os dois. O item compartilhado pode ganhar nota. A versão exclusiva continua barrada. Subir a nota não dispensa pesquisar nem o ok pra construir. Não deixe de anotar o peso do pedido só porque o cliente é grande.
